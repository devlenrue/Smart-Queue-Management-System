## What the system does

```text
Customer                          Staff                        Admin
────────                          ─────                        ─────
browse services                   see the waiting queue        create services & counters
join a queue      ──ticket──►     call next                    assign staff
track position    ◄─notify───     start / complete service     monitor live queues
cancel                            skip / no-show / recall      read reports
view history                      view own statistics          publish announcements
```

A customer picks a service, receives a ticket such as `FIN-023`, and watches their position, the number
now being served and an estimated wait — all computed by the server from the database, refreshed by
polling. Staff call tickets to a counter and move them through
`waiting → called → serving → completed`. Admins watch the whole thing and pull reports.

## Features

| | |
| --- | --- |
| **Authentication** | Registration, bcrypt-hashed passwords, JWT sessions with server-side revocation, change-password, four roles |
| **Authorisation** | `customer` · `staff` · `admin` · `super_admin`, enforced by middleware on every route and re-checked in the service layer |
| **Queue engine** | Join → server-issued ticket (`FIN-001`) → live position → call → serve → complete, plus cancel, skip, no-show and recall |
| **Concurrency safety** | Ticket numbers allocated under `SELECT … FOR UPDATE`; unique keys make a duplicate impossible even if the application is wrong |
| **Estimated wait** | `peopleAhead × averageServiceTime ÷ activeCounters`, blended with measured times once there is a sample. Documented and hand-checkable |
| **Notifications** | Written in the same transaction as the event that caused them; inbox with unread badge, filters and mark-all-read |
| **Announcements** | Draft → published → archived, fanned out to every active user on publish |
| **Service management** | Service CRUD, per-weekday opening hours, per-service queue settings, counters, staff postings |
| **Live monitoring** | Public queue board, staff console and an administrator's live monitor across every open queue |
| **Reporting** | Four management reports over any date range, with CSV export generated by the server |
| **Search, filter, paging** | Server-side across services, users, staff, tickets and notifications, with a per-endpoint sort allow-list |
| **Validation and errors** | zod on every input; one envelope, 34 stable error codes, no raw exception ever reaches a client |

## Quick start

```bash
# 1. database
mysql -u root -p -e "CREATE DATABASE smart_queue CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 2. api
cd server
cp .env.example .env          # set DATABASE_URL and JWT_SECRET
npm install
npm run db:migrate
npm run db:seed
npm run dev                   # http://localhost:5000/api/v1

# 3. client
cd ../mobile
flutter pub get
flutter run --dart-define=API_BASE_URL=http://localhost:5000/api/v1
```

Android emulator: use `http://10.0.2.2:5000/api/v1`. Physical device: your machine's LAN IP.

The Flutter client lives in [`mobile/`](mobile/) and is documented in [`mobile/README.md`](mobile/README.md).
Platform folders are not committed, so the first run needs `flutter create .` — see that README.

### Running without a MySQL server

The repository layer talks to an interface, not to MySQL directly, so the whole API and its test suite
can run on file-backed SQLite with the identical schema. Change one line in `.env`:

```bash
DATABASE_URL=sqlite://../database/local/dev.db
npm run db:reset      # migrate + seed in one step
npm run dev
```

MySQL remains the deployment target; this is only so the project can be marked on a machine without a
database server.

## Configuration

Everything is read from `server/.env`, copied from
[`server/.env.example`](server/.env.example). `src/config/env.ts` is the only file in the codebase
that touches `process.env`; it parses and validates on import, so a missing or nonsensical value
fails at start-up with a clear message rather than at 2 a.m. with `undefined`.

| Variable | Default | What it does |
| --- | --- | --- |
| `PORT` | `5000` | HTTP port |
| `NODE_ENV` | `development` | `development` · `test` · `production` |
| `TZ` | `Africa/Nairobi` | **All** date arithmetic — `queue_date`, opening hours, report ranges |
| `DATABASE_URL` | — | `mysql://user:pass@host:3306/smart_queue` or `sqlite://./path.db`. The scheme picks the dialect |
| `DB_POOL_SIZE` | `10` | MySQL pool size |
| `JWT_SECRET` | — | **Required**, at least 32 characters. Generate one with `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `JWT_EXPIRES_IN` | `7d` | Token lifetime |
| `BCRYPT_ROUNDS` | `10` | Password hashing cost |
| `CORS_ORIGIN` | `*` | Comma-separated allow-list. Never `*` in production |
| `RATE_LIMIT_WINDOW_MINUTES` | `15` | Window for all three limiters |
| `RATE_LIMIT_AUTH_MAX` | `30` | Login and register, per IP |
| `RATE_LIMIT_JOIN_MAX` | `20` | Queue joins, per IP |
| `RATE_LIMIT_API_MAX` | `1000` | Backstop over `/api/v1`, per IP |
| `QUEUE_DEFAULT_SERVICE_MINUTES` | `5` | Fallback average service time |
| `QUEUE_NOTIFY_THRESHOLD` | `3` | Notify a customer this many places from the front |
| `QUEUE_DEFAULT_MAX_SIZE` | `100` | Fallback daily queue cap |
| `SEED_PASSWORD` | `Password123!` | Password given to every seeded account |

The client takes one compile-time setting:

```bash
flutter run --dart-define=API_BASE_URL=http://localhost:5000/api/v1
```

Its default is `http://10.0.2.2:5000/api/v1`, the Android emulator's alias for your machine. Whatever
a build is pointed at is displayed under **Settings → Connection**.

## End-to-end walkthrough

The brief's success criteria (§85) are an executable script, not a claim:

```bash
cd server
npm run dev            # one terminal
npm run walkthrough    # another
```

It registers a customer, browses the live catalogue, takes a ticket, is refused a second one
(Rule 1), tracks its position, watches a clerk be refused a busy counter (Rule 5), gets called,
served and completed, is refused an illegal repeat, checks that another customer cannot read the
ticket, reads the notifications it generated, finds the visit in the administrator's daily report,
downloads the CSV, and confirms a customer cannot read a report at all. Fifteen steps, all through
documented endpoints against the real database.

A recorded run, and what each step proves, is in [`docs/walkthrough.md`](docs/walkthrough.md).

## Known limitations

[`docs/known-limitations.md`](docs/known-limitations.md) is the honest list, separated into what the
brief ruled out, what was traded deliberately, and what is simply unfinished. The headlines:

* Notifications are **polled, not pushed** — a closed app learns it was called when it is reopened.
* The live surfaces poll on a timer (5 s / 10 s / 15 s); there is no WebSocket.
* **Password reset is manual** — no email is sent; an administrator sets a new one at the desk.
* One institution per deployment; there is no tenant column.
* MySQL is the target. The SQLite fallback serialises writes with a mutex instead of `FOR UPDATE`, so
  the §60 concurrency guarantees are a MySQL claim, tested through the same code path.
* Reports are computed at read time — correct always, slower as history grows.
* Two Flutter test suites and the screenshots have not been run/taken; see the roadmap.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `JWT_SECRET must be at least 32 characters` at start-up | `.env` still has the placeholder. Generate one: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `ER_ACCESS_DENIED_ERROR` / `ECONNREFUSED 3306` | MySQL is not running, or `DATABASE_URL` is wrong. To carry on without it, set `DATABASE_URL=sqlite://../database/local/dev.db` and run `npm run db:reset` |
| `Unknown database 'smart_queue'` | Create it: `mysql -u root -p -e "CREATE DATABASE smart_queue CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"` |
| App shows "Cannot reach the server" on an **Android emulator** | `localhost` inside the emulator is the emulator. Use `http://10.0.2.2:5000/api/v1` — the default |
| Same, on a **physical device** | Use your machine's LAN IP, and make sure both are on the same network and your firewall allows port 5000 |
| Same, on **Android** with a plain `http://` URL | Android blocks cleartext by default. Add `android:usesCleartextTraffic="true"` to the `<application>` tag in `android/app/src/main/AndroidManifest.xml` |
| `flutter run` cannot find a platform | Platform folders are not committed. Run `flutter create .` inside `mobile/` first |
| `Target of URI doesn't exist: 'package:path_provider/…'` | `flutter pub get` — Phase 8 added a dependency |
| Login works, every other call returns `401` | The token expired (`JWT_EXPIRES_IN`, default 7 days) or the server restarted with a different `JWT_SECRET`. Sign in again |
| `429 RATE_LIMITED` while testing | You tripped a limiter. Raise `RATE_LIMIT_*` in `.env` and restart, or wait out the 15-minute window |
| Wrong day's tickets, or hours that look an hour out | `TZ` in `.env`. Every date decision the server makes uses it |
| Jest says "A worker process has failed to exit gracefully" | Run with `npm test` (which adds `--runInBand`) rather than bare `jest` |

## The part that matters

This is not a CRUD app with a queue table bolted on. The graded core is the **queue engine**:

* ticket numbers allocated under a `SELECT … FOR UPDATE` row lock so 25 simultaneous joins produce
  25 consecutive numbers and never a duplicate;
* a unique key on `(queue_id, sequence_number)` and a **generated column** that makes "one active ticket
  per user per service" a database guarantee rather than an application hope;
* positions and waiting-time estimates recomputed from live rows on every read — nothing cached, nothing
  hard-coded;
* an explicit state machine where every illegal transition is rejected with a 409 and every legal one is
  written inside a transaction together with its audit event and notification.

See [`docs/queue-engine.md`](docs/queue-engine.md).

## Academic note

Built as a university class project against an 88-section brief, incrementally, in ten phases
recorded in [`docs/roadmap.md`](docs/roadmap.md) — each phase designed, explained, implemented and
tested before the next was started.

Deliberately **not** included, per the brief's scope boundary: payments, machine learning,
blockchain, container orchestration, microservices and push-notification infrastructure. A queue for
one institution needs none of them, and adding them would hide the parts actually being marked.

The SQL is hand-written and parameterised rather than generated by an ORM; the migrations are
numbered and reversible; the schema is normalised with real foreign keys, unique constraints and
indexes; and the business rules that matter are enforced by the database as well as by the code, so
they hold even when the application is wrong.
